استخدم Git لتتبّع التغييرات في plug-in، والتراجع عن الأخطاء، ومشاركة التعليمات البرمجية بين الأجهزة.

## لماذا تنظّم التعليمات البرمجية؟

عندما يصبح لديك أكثر من برنامج نصي واحد، تُوفّر بنية مجلدات متسقة الوقت وتُبسّط التحكم في الإصدارات.

## إعداد بنية مجلد للتعليمات البرمجية

من أبسط طرق تنظيم المشاريع إنشاء **مجلد تعليمات برمجية** مخصّص على جهازك المحلي. داخل هذا المجلد، أنشئ مجلدات فرعية لكل مشروع أو مستودع. فيما يلي بنية موصى بها:

```plaintext
/home/your-username/code/
  ├── project1/
  ├── project2/
  └── project3/
```

يمثّل كل مجلد فرعي (مثل `project1`) **مستودعًا**، حيث تخزّن ملفات المشروع وتعليماته البرمجية.

## ما المقصود بالمستودع؟

**المستودع** (أو **repo**) هو في الأساس مجلد يتتبّعه Git. عند إنشاء مستودع محلي، تُهيّئ Git داخل ذلك المجلد، ما يتيح لك حفظ التغييرات على نسخة عبر الإنترنت.

### المستودعات المحلية والبعيدة

- **Local Repo**: المستودع المخزّن على جهازك، في أحد مجلدات مشروعك.
- **Remote Repo**: نسخة من المستودع مخزّنة عبر الإنترنت (على GitLab أو GitHub مثلًا).

## استخدام Git وGitHub

بعد إعداد بنية المجلدات، يمكنك تهيئة Git وربط مشاريعك المحلية بـ GitHub. اتبع هذه الخطوات للبدء:

### الخطوات الأساسية لاستخدام Git وGitHub

1. **تثبيت Git**
2. **إنشاء حساب GitHub**
3. **إنشاء مستودع فارغ على GitHub**
4. **تهيئة Git في مشروعك المحلي**
5. **ربط المستودع المحلي بـ GitHub**
6. **تجهيز الملفات (staging)**
7. **تنفيذ commit للتغييرات**
8. **دفع التغييرات إلى GitHub**
9. **عرض المستودع عبر الإنترنت**

### 1. تثبيت Git

إذا لم تكن قد ثبّت Git بعد، يمكنك ذلك على Linux باستخدام:

```sh
sudo apt install git
```

### 2. إنشاء حساب GitHub

إذا لم يكن لديك حساب، زُر [GitHub](https://github.com/) للتسجيل. بعد التسجيل، يمكنك إنشاء مستودعات على GitHub لتخزين تعليماتك البرمجية عبر الإنترنت.

### 3. إنشاء مستودع فارغ على GitHub

1. **تسجيل الدخول إلى GitHub**: انتقل إلى [GitHub](https://github.com/) وسجّل الدخول إلى حسابك.
2. **إنشاء مستودع جديد**:
   - انقر أيقونة **+** في الزاوية العلوية اليمنى واختر **New repository**.
   - أدخل اسم المستودع (مثل `your-repository`).
   - أضف وصفًا إن رغبت.
   - اختر **Public** أو **Private**.
   - **لا** تُهيّئ المستودع بـ README أو `.gitignore` أو ترخيص (لتجنّب التعارضات).
   - انقر **Create repository**.

### 4. تهيئة Git في مشروعك المحلي

لبدء تتبّع مجلد مشروع بـ Git، افتح الطرفية، وانتقل إلى مجلد المشروع، ثم نفّذ:

```sh
cd code/your/project/folder
git init
```

يُهيّئ هذا الأمر مستودع Git فارغًا في مجلد مشروعك.

### 5. ربط المستودع المحلي بـ GitHub

بعد إنشاء مستودع فارغ على GitHub، أضِفه كمستودع بعيد (remote) لمشروعك المحلي:

```sh
cd code/your/project/folder
git remote add origin https://github.com/your-username/your-repository.git
```

استبدل `your-username` و`your-repository` باسم مستخدم GitHub الفعلي واسم المستودع. يربط هذا الأمر مشروعك المحلي بالمستودع البعيد على GitHub.

### 6. تجهيز الملفات (staging)

قبل حفظ التغييرات في Git، عليك إخبار Git بالملفات التي عدّلتها وتريد حفظها. تُسمّى هذه العملية **staging**. استخدم الأمر التالي لتجهيز جميع الملفات المعدّلة أو الجديدة:

```sh
git add .
```

يُخبر Git بتتبّع التغييرات التي أجريتها على جميع ملفات المشروع. يمكنك أيضًا تجهيز ملفات محدّدة باستبدال `.` باسم الملف.

### 7. تنفيذ commit للتغييرات

بعد التجهيز، الخطوة التالية هي حفظ التغييرات (أي تنفيذ **commit**) في مستودع Git المحلي. عند كل commit، ضمّن رسالة تصف التغييرات. مثلًا:

```sh
git commit -m "Add new feature"
```

تتيح العلامة `-m` كتابة رسالة تلخّص التغييرات. تساعدك هذه الرسالة — وأي شخص آخر — على فهم ما تغيّر في هذا commit.

### 8. دفع التغييرات إلى GitHub

بعد تنفيذ commit محليًا، يمكنك **push** التغييرات إلى GitHub لتحديث المستودع البعيد. نفّذ الأمر التالي لرفع التغييرات:

```sh
git push -u origin main
```

الفرع `main` هو الفرع الافتراضي في GitHub حيث يُخزَّن التعليمات البرمجية. يرفع هذا الأمر التغييرات المحلية إلى المستودع البعيد، فيصبح بإمكانك الوصول إليها عبر الإنترنت.

### 9. عرض التعليمات البرمجية على GitHub

بعد push التعليمات البرمجية إلى GitHub، يمكنك عرض المستودع في واجهة GitHub على الويب. ستجد ملفات المستودع المحلي وسجل commit يوضّح التغييرات التي أجريتها.

## الخلاصة

بتنظيم تعليماتك البرمجية في مجلدات مخصّصة واستخدام GitHub لإدارة المستودعات ونسخها احتياطيًا، تبقى مشاريعك منظّمة وسهلة الوصول. عندما تصبح لديك نسخة عاملة من تعليماتك البرمجية، ادفعها إلى GitHub. بعد ذلك يمكنك تتبّع أي تغيير بسهولة عبر واجهة GitHub على الويب أو Visual Studio Code الذي يُبرز الأسطر المعدّلة. يتيح لك هذا الأسلوب مواصلة تحسين تعليماتك البرمجية وتوسيعها دون فقدان مسار التقدّم أو التغييرات.

Git والمنصّات مثل GitHub وGitLab أدوات قوية. وعلى الرغم من تعقّدها أحيانًا، تتوفر موارد كثيرة عبر الإنترنت لفهمها. من أهم ما وجدته مساعدي الذكاء الاصطناعي مثل ChatGPT: صِف ما تريد إنجازه، وسيرشدونك خطوة بخطوة.

## مسرد المصطلحات

فيما يلي مصطلحات شائعة عند العمل مع Git وGitHub:

- **Commit**: لقطة للتغييرات في المستودع. يتضمّن كل commit رسالة تصف ما تغيّر، ويُنشئ سجلًا تاريخيًا يمكنك الرجوع إليه أو التراجع إليه لاحقًا.
- **Repository (Repo)**: مجموعة ملفات وسجلّها الذي يتتبّعه Git. قد يكون المستودع محليًا على جهازك أو بعيدًا على منصّات مثل GitHub. عادةً يُخزَّن كل مشروع في مستودعه الخاص.
- **Remote**: المستودع البعيد هو نسخة من مشروعك مستضافة على منصّة مثل GitHub. يرتبط الإصدار المحلي على جهازك بهذا المستودع البعيد لتتمكن من رفع التغييرات (push) وتنزيلها (pull).
- **Staging**: عملية تجهيز الملفات لـ commit. عند تجهيز ملف، تُخبر Git أنك تريد تضمينه في commit التالي. يتيح لك staging اختيار التغييرات التي تُدرَج في commit.
- **Push**: إرسال التغييرات التي نُفّذ commit لها من المستودع المحلي إلى مستودع بعيد (مثل GitHub)، ليتمكن الآخرون من الوصول إلى الإصدار المحدّث من تعليماتك البرمجية.
- **Pull**: جلب التغييرات من مستودع بعيد لتحديث نسختك المحلية. تُجري pull عندما تريد مزامنة المستودع المحلي مع أحدث إصدار من المستودع البعيد.
- **Origin**: الاسم الافتراضي للمستودع البعيد عند ربط المستودع المحلي بمستودع بعيد لأول مرة. يشير عادةً إلى عنوان URL الرئيسي لمشروعك على GitHub.
